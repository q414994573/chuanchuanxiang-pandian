# 川川香订货总控台：接手与维护说明

更新日期：2026-10-30（韩国时间）。本说明以 v55 已发布代码为准；实际发布状态看 [v55 验证记录](v55/regression.md)。不要把代码已完成、模拟器已通过、线上已发布混成一件事。

## 先读这里

这是一套手机盘货、共同订货和供应商文字复制工具。主要使用 iPhone，也要兼容三星和 KakaoTalk 内置浏览器。

正式入口：https://q414994573.github.io/chuanchuanxiang-pandian/ordering/

旧兼容入口在根目录 `/`；`/redesign-preview/`、`/cloud-test/` 是测试入口。不能把测试入口或旧入口当成正式新版验收对象。仓库由 GitHub Pages 发布，数据库是 Firebase 项目 `chuanchuanxiang-order`。

需要接手的人按这个顺序阅读：本文件 → [版本与漏洞记录](改版与漏洞记录.md) → [工作日志](工作日志.md) → 本次测试报告 → 对应代码。旧日志记录的是当时情况；例如早期129种商品、定稿前复制流程与当前版本不同。冲突时先核对最新用户确认、当前代码和对应测试，不能直接照搬旧文档。

## 不得擅自改变的业务规则

- 商品稳定ID是身份，不靠名称或数组下标识别。用户没有授权时，不改主名称、分类、单位、原来走动顺序，不合并相似商品，不批量翻译成韩文。
- v55 新建目录138种：韩国50、中国70、其他13、饮料5。饮料在原始数据仍属 `other`，界面和供应商导出通过 `count-flow.cjs` 分成四组；中国食品里的茶饮不能擅自挪进饮料组。
- 历史129、137种目录保留原快照；新增商品只进入新建目录，不强行扩写正在进行的旧盘货、已定稿订单或历史记录。商品扩容必须同时校验客户端、云端规则、恢复、导出与旧版本兼容。
- 库存与订货独立，单位可以不同。空白不等于0；填0不自动订货；不得猜测数字、单位或自动换算。
- 新建盘货数量为空，不将存档参考数量当作今天数量。`current-order.json` 中的来源日期和来源哈希是历史参考，不是实时库存证明。
- `감자수제비` 按大包填，1大包=2小包是提醒，不自动乘除。`고수` 保留复看冰箱提醒。
- 特殊单位选择保留：`cn:45` 的订货单位、`other:11` 的容器单位按现有选项校验；不能把库存单位默认值误作订货单位。
- `kr:59` 显示、搜索及导出均为 `고추장(1kg)`。旧快照可能存2kg，只做有针对性的兼容，不改其库存、数量、单位或原快照。不能把兼容规则扩大为允许任意商品改名。
- 未处理、已确认、不订、待定是不同状态。编辑后需要重新确认；待定商品不能误计已完成或漏过定稿检查。
- 两个有效成员在新版共同盘货具有同等业务权限，都能定稿、解除定稿。不得恢复“老板审批/单方审核”流程。旧私有草稿的owner限制仅作兼容，不能推论为新版业务权限。
- 定稿后禁止编辑；解除定稿后可共同修改，供应商导出重新锁住。复制成功不代表消息已发送。未经明确指示不得自动发给供应商。
- 不增加最低备货量、星标、重点商品、自动补货。界面布局、声音、语音和震动逻辑不随一次商品新增随意改动。

## 软件如何运行

`ordering/index.html` 加载核心模块、共用界面CSS与 `redesign-preview/preview.bundle.js`。源码入口是 `redesign-preview/preview.js`，不要只修改压缩bundle。

`count-core.js` 定义新建、编辑、确认、校验和旧目录适配。`count-flow.cjs` 定义四组显示及导航；`search.cjs` 和 `aliases.json` 支持中文、韩文、首字母和多商品搜索；`product-names.cjs` 管理已确认的名称显示例外。

`cloud/shared-count.js` 通过 Firestore 事务维护当前共同盘货。正式头 `sharedCounts/current`，测试头 `sharedCounts/test-current`，历史订单在 `orders`，修订在对应 `revisions`，替换未定稿草稿前保存 `archives`。

停止输入约1.5秒后尝试保存，实时监听接收他人修改。它不是无条件秒级同步。不同逻辑格以基线、本机、远端三方合并；同格不同值产生冲突并保留本机输入，不能静默选一方覆盖。

事务成功返回已提交版本；不能用随后一次独立读取的旧值当保存确认。监听回调不能覆盖保存期间的新输入，也不能在原生文字输入时销毁输入框。历史查看不能被当前共同盘货更新抢回。

定稿/解除定稿应原子更新阶段、订单和修订。新建空白盘货必须保留原草稿或历史，拒绝过时及并发替换。实时监听已确认版本用于供应商复制；不能把复制按钮改回每点一次都先远程读取，破坏手机首次点击复制。

`firestore.rules` 限制有效成员、身份、版本递增、原子配对、目录大小与键集合、数量格式、审计记录不可修改删除等。规则不是任意JSON正文的完整语义解析器，不能声称能抵御已授权成员恶意构造全部正文。权限测试不得因此省略。

## 新增一个商品的完整步骤

1. 先记录名称、单位、分类、是否有库存栏，检查现有名称和ID，分配新稳定ID；不能复用删除过的ID。
2. 保留上一完整目录版本，再更新 `current-order.json` 与搜索别名。新增库存和订货均为空。检查旧商品逐项对象完全不变。
3. 更新 `sourceFor` 和有效目录校验：必须接受明确的旧目录，拒绝缺商品、重复ID、错分类、错名称等畸形目录。不能仅“数量达到某个范围”就放行。
4. 更新 `scripts/generate-rules.cjs` 支持的目录版本并运行 `npm run rules:generate`。比较规则差异，权限、审计、锁定不能被顺手放宽。
5. 更新当前目录数量、分类末尾、导航下标等测试期待；旧版本专用测试仍使用旧目录。新增同等行为和旧版本恢复测试。
6. 构建两个bundle，统一入口缓存版本；运行下文全套检查。
7. 先部署并核验兼容新旧目录的云端规则，再发布网页。否则新目录可能能显示却不能定稿。规则未发布时，不先上线138种页面。
8. 新商品只在新建盘货出现属于历史保留规则，不要为了让旧表立刻出现而修改营业数据。

## 怎么测试

安装仓库锁定依赖：`npm ci`。先读 `package.json`，不要随测试随意升级生产依赖。Node、Java、浏览器版本应写入结果。

逻辑全套：`npm test`。每个断言检查实际结果；不能只看控制台有PASS、运行没崩溃、或把跳过算通过。若测试进程留下定时器，应定位具体测试并记录，不把仍未结束的进程算成功。

构建：`npm run build`、`npm run build:preview`。规则生成应再次运行并验证无额外差异。

云端隔离测试依次运行：

- `npm run test:rules`
- `npm run test:shared`
- `npm run test:shared-view`
- `npm run test:shared-transitions`
- `npm run test:supplier-rehearsal`
- `node_modules/.bin/firebase emulators:exec --only firestore --project demo-ccx-catalog-versions "node tests/catalog-versions.test.mjs"`

全部用本地demo模拟器，不使用真实订单测试。拒绝非法操作的用例可能打印 `PERMISSION_DENIED`，要看它是否为预期拒绝、最终断言及退出码，不能只看关键词。

浏览器测试是 `tests/*.browser.cjs`，通过 `CCX_PLAYWRIGHT_MODULE` 指定已安装Playwright、`CCX_BROWSER_ENGINE` 指定chromium/webkit、`CCX_BROWSER_SOURCE` 指向当前checkout、`CCX_BROWSER_OUTPUT` 保存报告。覆盖430/375/320宽度、owner/editor、草稿/待定/定稿。必须包含搜索进度、语音导航、原生输入、搜索页、手机流程、布局、声音、跨分类搜索、截图问题、新商品、正式bundle启动与旧规格回归。

完整运行入口：`python3 scripts/run-browser-regression.py`。它依次运行全部套件并输出逐套JSON；默认两个引擎，可用 `CCX_BROWSER_OUTPUT_ROOT` 指定报告目录。运行前必须安装浏览器及其系统依赖。

浏览器测试采用隔离fixture，不向生产Firebase写入。记录每套退出码、案例结果、页面错误和源码哈希。失败必须先保留证据再定位；单项重跑通过不抹掉首次失败。如果浏览器缺失、下载失败或系统依赖不全，明确标记未执行，不引用上一轮通过结果冒充本轮。

真机另验：iPhone输入法联想/组合输入、键盘弹出和收起、Safari及KakaoTalk、前后台、弱网/断网重连、两手机同格冲突、复制权限、实际声音与震动。桌面WebKit不等于真实iPhone验收。

## 必须反复跑的历史问题

- 输入 `大葱腐竹粉丝`：无论起始分类，结果必须包含 `kr:7`、`cn:33`、`cn:75`；不能只显示韩国的大葱。搜索导航也要跨这三个结果。
- 输入新商品与上述商品的连写、分隔写法，仍不能被分类筛选截断。
- 点击未来商品不能把中间商品误计已盘；进度必须来自真实完成状态。
- 保存期间继续输入、监听先后颠倒、同格同值和同格不同值，不能丢数字或误报冲突。
- 解除定稿后留在正确订单状态，不能误提示已登录用户去登录。
- 旧2kg辣椒酱在新版、旧入口、本机导出与云端导出都显示1kg，原数据保持不变。
- 新旧目录129/137/138均可读取、保存、定稿/解锁和恢复；混合拼凑及少一项目录应拒绝。
- 搜索筛选不能截掉供应商整单；不同供应商不串货，饮料不混进其他组。
- 全部主名称保留用户选择，韩文完整词不应随首字母兜底乱匹配。

## 发布、回退和交接

提交前看完整diff，确认没有测试输出、node_modules、凭据、真实营业数据混入。代码/文档进入Git，原历史备份不修改。测试记录包含日期、基线提交、源码哈希、测试命令、通过失败数量、未验证内容和发布状态。

GitHub Pages构建成功后，核验线上入口、目录、核心、别名、bundle字节与测试版本一致。云端规则是单独发布动作，GitHub提交规则文件不代表Firebase规则已生效。

回退用新的恢复提交，保留后续历史；页面与规则的目录兼容必须配套。已有新目录订单时不能回退为只识别旧目录的客户端。不要清空Firebase、删除修订、删除手机草稿或重写历史作为回退手段。

每次变更更新本文件相关规则，在 [改版与漏洞记录](改版与漏洞记录.md) 和 [工作日志](工作日志.md) 追加记录。不要写“没有问题”，应写“哪些版本、哪些场景、哪些检查通过，哪些尚未验证”。
