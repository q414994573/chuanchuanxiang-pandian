# v41 · 已定稿订单一键复制 / 分享

日期：2026-10-25（韩国时间）

## 适用规则

- 盘货、定稿、审核、发送按双方当面交接顺序进行，不会同时修改或同时操作同一订单。
- 两个账号完全共用复制、分享、预览、离线功能，不根据 `owner` / `editor` 分叉。
- 任一账号解除定稿、修改后，必须重新保存并定稿，才能复制、分享。
- 已经成功通过云端读取或定稿事务确认的最终订单可以在当前页面离线导出；断线时明确提示。
- 原始商品名称、库存单位、订货数量及供应商分类输出格式保持不变。

## 实现

- 原流程的首次 `supplierExport()` 和后续 `deliverPrepared()` 每次都强制执行 `api.read()`，导致反复等待网络。
- 新版在 `acceptOrder()` 成功加载服务器订单、或 `changeOrderStage()` 确认定稿后，记录 `orderBase` 作为已确认版本。
- 导出前仅检查本地订单是否定稿、有无未保存改动、订单编号及版本、数量、单位、库存状态与 `orderBase` 是否一致；随后立刻执行复制或系统分享。
- “查看本类订货文字”是可选预览，不是强制第二次点击；预览继续依据本地版本、会话和内容签名判断是否失效。
- 网络失联不阻止已确认版本导出，但未保存、未确认或解除定稿的订单绝不可导出。
- HTML 添加 `v=20261025-v41` 缓存版本，两个入口加载同一脚本。

## 边界条件

- 严格依赖已约定的串行交接：如果双方违背规则、在两台设备上同时操作，旧页面可能在收到远程变化通知前短暂保有先前定稿版。不能把实时同步当成跨设备原子锁。
- 离线导出是**已打开的当前页面**中成功确认的定稿版；刷新并重新登录仍需要网络。
- 无法从自动化单元测试保证真实 iPhone 系统弹窗耗时，需要手机做最后一轮实际操作验证。
- 所有 Firebase 模拟器测试使用 `demo-*` 项目，不读写正式订单。
