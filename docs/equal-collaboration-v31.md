# 双账号共同盘货 v31

## 当前业务规则

- `/ordering/` 固定网址不变。dawei / laobanniang 业务权限与界面相同，账号身份保留用于修改记录。
- 正式 `sharedCounts/current`、预览 `sharedCounts/test-current` 各自只有一个当前草稿。库存与订货、已盘状态一起同步，光标/搜索/所在分类各自独立。
- 输入停止1.5秒后尝试事务保存；对方通过服务端快照监听接收。不是每1.5秒无条件轮询，也不保证断网时秒级同步。
- 不同逻辑格三方合并；同格冲突保留本机输入并暂停自动保存。用户可下载本机副本后读取云端重新核对。未上传内容不直接覆盖远端。
- 任一成员可定稿。必须完成盘货、保存并排除冲突；订单、共享阶段、审计记录一次事务写入。定稿后双方只读并可复制分享；解除定稿再次开放共同编辑，供应商导出重新锁住。
- 同时开始下一次盘货会汇合到同一份草稿。历史订单继续保留。查看历史不会被当前草稿的实时更新替换。
- 供应商复制/分享仍先读取服务器核对当前定稿版本；复制成功不表示已发送。

## 兼容与安全

- 原私有 countDrafts/liveCountDrafts、历史 orders、旧根页面均保留，不删除或批量迁移。owner 原私有草稿权限只为兼容恢复保留；新协作入口不使用私有草稿作为实时写入目标。
- 首次进入如有不同的未提交本机草稿，会保留副本并要求核对，避免静默丢失。恢复备份不能覆盖正在进行的共同草稿。
- 已登录且 active 的 owner/editor 都有相同新业务权限；匿名/停用账号拒绝。成员名单禁止客户端改写。订单与审计禁止删除，版本必须递增、身份必须匹配、阶段必须配套事务。旧 API 无法绕过当前共享盘货的定稿锁。
- Firestore 规则约束结构、身份、大小和原子状态；JSON 草稿内部语义另由客户端校验，不应声称能抵御已授权成员蓄意伪造全部草稿正文。此版本不增加任何公共读取或管理员权限。
- 测试为本地 Firebase emulator，未往正式订单写入测试数据。线上规则从控制台发布并验证，页面通过 GitHub Pages 发布。
